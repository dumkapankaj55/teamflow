# TeamFlow production deployment

This guide deploys the existing React/Vite client to Vercel, the Express API to Render, and MongoDB to Atlas. It does not change the application stack.

## Before deploying

The API validates production configuration at startup. Configure real HTTPS frontend URLs, Resend credentials and a verified sender, and Cloudflare Turnstile production keys; development/test values are rejected. `CLIENT_URL` must be the exact frontend origin (no trailing slash), and that same origin must appear in `CORS_ORIGINS`.

The frontend uses `VITE_API_URL` as the Axios API base and sends credentialed requests. The API sets the refresh cookie as `HttpOnly`, `Secure`, and `SameSite=None` for the separate Vercel and Render origins. Some browser privacy settings restrict cross-site cookies; using custom domains on the same site (for example `app.example.com` and `api.example.com`) improves compatibility.

## 1. Create the MongoDB Atlas database

1. Create an account at [MongoDB Atlas](https://www.mongodb.com/atlas) and create a cluster in a region near the Render service.
2. In **Database Access**, create a database user with a unique, strong password. Grant only `readWrite` on the `teamflow` database.
3. In **Network Access**, allow Render's outbound IP addresses if they are available for the selected Render plan.
   - If the plan has no fixed outbound IPs, Atlas may require `0.0.0.0/0` for Render connectivity. This exposes the database network endpoint broadly; use a strong unique database password, least-privilege database access, TLS, and rotate credentials if exposed.
4. In **Connect → Drivers**, copy the Node.js connection string. Replace the password placeholder and set the database name to `teamflow`, for example `mongodb+srv://<db-user>:<encoded-password>@<cluster-host>/teamflow?retryWrites=true&w=majority`.
5. Keep this URI private. Add it only to Render's `MONGODB_URI`; do not commit it or put it in a `VITE_*` variable.
6. Do not select or drop any existing database. The application connects to the configured URI and performs its existing index migration at startup.

## 2. Create and deploy the Vercel frontend

1. Create a Vercel account and import `dumkapankaj55/teamflow` from GitHub.
2. Set **Root Directory** to `client`. Keep the project as a Vite application.
3. Set **Build Command** to `npm run build` and **Output Directory** to `dist` (also declared in `client/vercel.json`).
4. Add these Production Environment Variables:
   - `VITE_API_URL`: temporary value `https://replace-with-render-service.onrender.com/api/v1`; replace it after the Render service is created.
   - `VITE_TURNSTILE_SITE_KEY`: the public site key for the production Cloudflare Turnstile widget.
5. Deploy once to obtain the exact Vercel production URL. Do not expect login or API functionality until the Render API is available and `VITE_API_URL` is updated.
6. In Cloudflare Turnstile, register the Vercel production hostname (and any custom frontend hostname) and use the matching production site/secret key pair.

## 3. Deploy the Render API

1. Create a Render account, choose **New → Blueprint**, and connect the same GitHub repository.
2. Render reads the root `render.yaml`. The service root is the repository root, dependencies install with `npm ci`, the start command is `npm run start --workspace server`, and the health check is `/api/v1/health`.
3. Set the Blueprint's `sync: false` values in Render's environment settings. The `ACCESS_TOKEN_SECRET` is generated by the Blueprint. Use a unique random value of at least 32 characters if you need to supply it manually.
4. Set the following backend variables. Use actual values, never the examples or test secrets:

| Variable | Production value |
| --- | --- |
| `NODE_ENV` | `production` |
| `MONGODB_URI` | Atlas URI for the `teamflow` database |
| `ACCESS_TOKEN_SECRET` | Unique random secret, at least 32 characters |
| `ACCESS_TOKEN_TTL` | `15m` |
| `REFRESH_TOKEN_TTL_DAYS` | `30` |
| `COOKIE_NAME` | `teamflow_refresh` |
| `COOKIE_SECURE` | `true` |
| `COOKIE_SAME_SITE` | `none` |
| `CORS_ORIGINS` | Exact comma-separated HTTPS frontend origins, no trailing slash |
| `CLIENT_URL` | Exact canonical Vercel/custom frontend origin, no trailing slash |
| `PASSWORD_RESET_URL` | Full frontend URL ending in `/reset-password` |
| `REQUIRE_EMAIL_VERIFICATION` | `true` |
| `RESEND_API_KEY` | Resend API key |
| `RESEND_FROM_EMAIL` | Verified Resend sender, for example `TeamFlow <no-reply@example.com>` |
| `TURNSTILE_SITE_KEY` | Production site key for Cloudflare Turnstile |
| `TURNSTILE_SECRET_KEY` | Matching production secret key; backend only |

`PORT` is supplied by Render and is read by the server, so do not hardcode a port. The production API also requires HTTPS `CLIENT_URL`, `PASSWORD_RESET_URL`, and `CORS_ORIGINS`; `CORS_ORIGINS` must include `CLIENT_URL`. Configure Vercel preview/custom origins explicitly if those environments should call this API. Wildcard origins are not supported.

5. Wait for the Render deploy to finish. A healthy service must pass its health check; then test:

```powershell
Invoke-RestMethod https://<render-service>.onrender.com/api/v1/health
Invoke-RestMethod https://<render-service>.onrender.com/api/v1/health/ready
```

`/health` confirms the API process is responding. `/health/ready` must report `database: connected` before testing application flows.

## 4. Connect Vercel to Render

1. Copy the actual Render service URL from its dashboard.
2. In Vercel Production Environment Variables, set `VITE_API_URL` to `https://<render-service>.onrender.com/api/v1` (no trailing slash).
3. Redeploy the Vercel frontend so Vite embeds the production API URL in the client build.
4. Verify Render `CORS_ORIGINS` contains the exact Vercel production origin, such as `https://teamflow.vercel.app`, with no path or trailing slash. If you use a custom domain, add its exact origin too. `CLIENT_URL` should be the canonical frontend origin used by verification and invitation emails.
5. Add the same frontend hostname to the Turnstile widget's allowed hostnames. Keep `TURNSTILE_SECRET_KEY` only in Render.

## Environment variable checklist

- **Render:** `NODE_ENV`, `MONGODB_URI`, `ACCESS_TOKEN_SECRET`, `ACCESS_TOKEN_TTL`, `REFRESH_TOKEN_TTL_DAYS`, `COOKIE_NAME`, `COOKIE_SECURE`, `COOKIE_SAME_SITE`, `CORS_ORIGINS`, `CLIENT_URL`, `PASSWORD_RESET_URL`, `REQUIRE_EMAIL_VERIFICATION`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`.
- **Vercel:** `VITE_API_URL`, `VITE_TURNSTILE_SITE_KEY`.
- **Optional billing:** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_PRO`, `STRIPE_PRICE_ENTERPRISE`, and `SALES_EMAIL` (Resend settings are needed for sales enquiries). These names match the existing server configuration.
- **Never place private values in Vercel:** database URI, JWT secret, Resend API key, Turnstile secret, or Stripe secret.

## Local verification

From the repository root, with a reachable test MongoDB configured as `MONGODB_URI`:

```powershell
npm install
npm test
npm run build
npm run lint
```

The backend tests connect to MongoDB; they are not a substitute for testing against the production Atlas database. Never point automated tests at a database containing production data.

## Production smoke-test checklist

Use a test account and a non-production workspace:

1. Open the Vercel site and confirm the browser console has no CORS or mixed-content errors.
2. Register a user; confirm the verification email links back to the deployed frontend and verify the account.
3. Sign in; inspect browser storage to confirm the refresh token is not readable by JavaScript. The cookie should be `HttpOnly`, `Secure`, and `SameSite=None`.
4. Refresh the page and confirm the session is restored through refresh-token rotation. Sign out and confirm subsequent protected requests require login.
5. Test forgot-password and reset-password email links, including Cloudflare Turnstile on the reset form.
6. Create an organization, invite a member, and accept the invitation from its email link.
7. Test project/task and Analytics views; verify that one organization cannot access another organization's data.
8. Check Render logs for startup, Atlas, Resend, and environment errors. Do not publish logs containing connection strings or secrets.

## Common deployment issues

- **Render exits during startup:** check required environment variables, ensure frontend URLs are HTTPS and have no trailing slash, ensure `CLIENT_URL` is included in `CORS_ORIGINS`, and confirm the Atlas URI and Network Access rules.
- **Atlas connection timeout:** verify the username/password URL encoding, cluster state, database user privileges, and Render outbound-IP allowlist.
- **CORS or refresh requests fail:** use the exact Vercel origin (scheme and hostname, no path), `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=none`, and Axios credentials (already enabled in the client). Redeploy after changing variables.
- **Emails contain localhost or the wrong domain:** set `CLIENT_URL` and `PASSWORD_RESET_URL` to the deployed frontend URLs, and verify the Resend sender domain and `RESEND_FROM_EMAIL`.
- **Turnstile fails:** make sure the Vercel hostname is allowlisted, the site key matches Vercel's `VITE_TURNSTILE_SITE_KEY`, and the corresponding secret is set only in Render.
- **Direct page refresh returns 404:** confirm the Vercel project uses `client` as its root and the SPA rewrite in `client/vercel.json`.
- **Frontend calls its own domain for the API:** set the full Render API URL in Vercel's `VITE_API_URL` and redeploy; Vite variables are embedded at build time.
- **Auth works in one browser but not another:** third-party cookie restrictions may block Vercel-to-Render cookies. Consider deploying both services on custom subdomains of the same registrable domain.

This repository configuration does not itself create cloud accounts or guarantee a live deployment. Verify both Render health endpoints and complete the smoke tests above after deployment.
